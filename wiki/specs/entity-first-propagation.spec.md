## Validated Behavior

M5 narrows kafkaman's V1 product surface to compact domain entity snapshots for
distributed caches. Durable send, durable receive, retry, DLQ, and replay remain
because they support reliable entity-cache propagation; they are not a general
durable job-queue promise.

### Entity message surface

`KafkaMessage` now requires `entity_key(&self) -> String`. `RetentionClass`,
`KafkaMessage::retention_class`, and `MessageDescriptor.retention_class` are
removed, so every registered kafkaman message type is treated as an in-purview
compact entity snapshot.

`partition_key()` remains optional. If a message supplies no partition key,
`OutboxRow::record_key()` falls back to `entity_key`; keyless publication is not
allowed to scatter one entity's snapshots across Kafka partitions, because the
cache convergence guard compares offsets only within one topic and partition.

### Cache table storage

Each registered message type can have a per-type cache table generated by
`CacheTable` / `CreateCacheTable`. Fresh cache tables are named
`cache_<message_type>` and contain:

- `entity_key TEXT PRIMARY KEY`
- `payload JSONB NOT NULL`
- `applied_topic TEXT NOT NULL`
- `applied_partition INTEGER NOT NULL`
- `applied_offset BIGINT NOT NULL`
- `deleted BOOLEAN NOT NULL DEFAULT false`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

The received table now also carries `entity_key` through `ReceivedRow` and
`ReceivedMeta`. `AddReceivedEntityKey` upgrades received tables created before
this column existed.

### Receive-side convergence

Receive dispatch still runs the handler first. On handler success,
`apply_successful_dispatch` applies the cache update and marks the received row
`Processed` in the same transaction. A rollback of that transaction rolls back
both the handler effects and the cache/processed mark.

The cache upsert resolves entity identity from the persisted received-row
`entity_key` column, with a Kafka record-key fallback only for legacy rows
written before that column existed. There is deliberately no
`kafkaman-entity-key` header tier and no fallback to `message_id`; a row with no
resolvable entity key fails with `MissingEntityKey`.

The guarded upsert inserts a first row or updates an existing row only when the
incoming record matches the currently applied topic and partition and has a
higher `source_offset`. Older retry, redrive, redelivery, and concurrent
dispatch rows are therefore processed without regressing cache state.

`CacheApplyOutcome::Applied` records forward progress. `Ignored` records a
correct stale-record loss. Topic or partition mismatch is reported as
`CacheOriginMismatch`, not as a normal ignored record, because offsets are not
comparable across origins. `MissingEntityKey` and `CacheOriginMismatch` are
terminal receive failures on the first attempt.

### Outbound per-entity supersede

Outbox rows carry nullable `entity_key`; fresh outbox tables include it and
`AddOutboxEntityKey` upgrades old tables. `OutboxStatus` includes
`Superseded`, and relay claiming excludes superseded rows.

`enqueue_on_connection` writes the entity key, rejects user-supplied reserved
`kafkaman-*` headers, and adds an internal `kafkaman-entity-key` header only
when the Kafka record key differs from the entity key. That header is for
foreign consumers; kafkaman's own receive path resolves entity identity from the
typed payload and received-row column.

For a valid entity message, enqueue takes a transaction-scoped advisory lock
keyed by schema, message type, and entity key before deciding whether to
supersede. Under that lock, a new row marks existing same-entity `Pending` rows
as `Superseded` before inserting the replacement. Rows already `Publishing` are
not superseded; newer `Pending` rows for the same entity are blocked from relay
claiming until the publishing row reaches a terminal status.

Claim-time pending collapse closes the publish-failure variant of the same
ordering problem: if an older `Publishing` row fails back to `Pending` after a
newer row was inserted, the next relay claim collapses stale pending siblings so
the older state cannot publish at a higher Kafka offset than the newer state.

### Replay and metadata

`Replay::outbox` is rejected with `UnsafeOutboxReplay`. Row-sourced outbox replay
is unsafe under the offset convergence ordinal because republishing stale state
creates a fresh, higher Kafka offset that every cache would treat as current.
`Replay::received` remains valid because inbound redrive keeps the original
`source_offset`.

The rdkafka publisher emits producer metadata as reserved headers, including
`kafkaman-occurred-at` and `kafkaman-idempotency-source`. Ingest preserves
well-formed idempotency source JSON, drops malformed source JSON to `NULL`
without rejecting the record, and rejects malformed `kafkaman-occurred-at`
because silently restamping would replace event time with consumer arrival time.

The rdkafka producer is configured with `enable.idempotence=true` and `acks=all`
so relay retries after uncertain broker outcomes do not create unnecessary
duplicate records at new offsets.

### Retry and outbox retention

Receive retry backoff remains exponential and capped, but M5 adds equal jitter:
the actual delay lands in `[base / 2, base]`. Tests that previously asserted an
exact `next_attempt_at` now assert the window.

Outbox retention is opt-in. `purge_outbox_once(pool, table, &PurgeConfig)` deletes
one bounded batch of old terminal rows, and `run_purger(pool, table, cfg,
shutdown)` loops that primitive. By default retention reclaims `Published` and
`Superseded` rows older than one week in 1,000-row batches, sleeps 60 seconds
between empty sweeps, and spares `Failed` rows. A config opt-in may include
`Failed` rows. Received tables and cache tables are not purged.

Fresh outbox tables include the terminal-status retention index, and
`AddOutboxRetentionIndex` upgrades existing tables. The index build blocks
writes because changesets apply inside a transaction and cannot use
`CREATE INDEX CONCURRENTLY`.

## Limitations

M5 does not include cache bootstrap/readiness typestate. Compacted-topic replay
from offset 0, `cache_state`, per-instance cache consumer groups, and the
`Cache<Bootstrapping> -> Cache<Ready>` surface remain proposal 10 work.

The two-service distributed-cache example is not part of this closeout. It
remains the active wiring proof in a separate worktree: two services, two
databases, HTTP-only assertions, and end-to-end cache convergence.

Broker topic validation is not implemented. kafkaman does not yet check at boot
that entity topics use `cleanup.policy=compact` alone.

There is no public advisory origin-intent enum yet. The accepted decision still
requires intent to be advisory and forward-compatible, but M5 does not expose or
test that API.

There is no state-sourced republish API yet. M5 validates the negative half:
row-sourced `Replay::outbox` is rejected. A positive resync surface must re-read
current domain state and enqueue through the normal supersede path.

Topic-lifecycle invalidation is partial. A per-row origin mismatch fails
terminally as `CacheOriginMismatch`, but there is no broker topic-ID detection,
global consecutive-regression circuit breaker, or forced re-bootstrap hook.

Soft-delete-first is not validated as a domain deletion workflow. Cache tables
have a `deleted` column, but M5 does not yet define a typed deletion surface,
foreign tombstone ingestion, or soft-delete row reclamation.
